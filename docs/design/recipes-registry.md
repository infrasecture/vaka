# Design: vaka Recipes Registry

Status: draft for discussion
Scope: `vaka get`, `vaka search`, `vaka recipes`, `vaka registry` and the
registry repository format. Nothing here is implemented yet.

## 1. Concept

A **recipe** is a ready-to-run, security-hardened compose project: a
`docker-compose.yaml`/`compose.yaml` plus a `vaka.yaml` egress policy, together
with any supporting files (README, launcher scripts, sidecar configs,
`.env.example`). `examples/codex` is the prototype: it ships a README, a
`myCodex` launcher, a prestart script, a LiteLLM config and a
`docker-compose.yaml → compose.yaml` symlink — so a recipe is a *directory*,
not just two YAML files.

A **registry** is a published catalog of versioned recipes that vaka can
search, fetch, verify, and update — the docker-registry / app-store experience:

```bash
vaka search agent                 # browse the catalog(s)
vaka recipes info codex           # metadata, required env, policy summary
vaka get codex                    # fetch latest into ./codex, verified
vaka get codex                    # later: same command updates it
cd codex && vaka up               # vaka never runs a recipe by itself
```

## 2. Two formats: authoring vs distribution

The key design decision is to separate how recipes are *written* from how they
are *consumed*. Consuming recipes by cloning git repos would force a git
dependency, give no immutable versioning, no integrity artifact, and no cheap
catalog. Instead we borrow the proven Helm chart-repository model:

**Authoring format.** A git repository — officially
`github.com/infrasecture/vaka-registry` — where every top-level directory is
one recipe:

```
vaka-registry/
├── codex/
│   ├── recipe.yaml          # manifest (new, required)
│   ├── compose.yaml
│   ├── docker-compose.yaml -> compose.yaml
│   ├── vaka.yaml
│   ├── README.md
│   ├── .env.example
│   └── ...any supporting files
├── claude-code/
│   └── ...
└── .github/workflows/       # validate + package + publish index
```

**Distribution format (what vaka talks to).** A registry is just two kinds of
static HTTPS artifacts, generated by the repo's CI:

- `index.yaml` — the catalog: every recipe, every version, description, tags,
  required env vars, a policy summary, tarball URL and `sha256` digest.
- `<name>-<version>.tar.gz` — one recipe directory, packaged at release time.

Because the distribution format is static files, a registry can be GitHub
Releases + Pages, an S3 bucket, or a plain file server behind a corporate
proxy — no server component, trivially mirrorable for air-gapped use, and
`file://` support is nearly free for testing.

## 3. The recipe manifest: `recipe.yaml`

Each recipe directory must contain a manifest; CI validates it and builds the
index from it:

```yaml
apiVersion: recipes.vaka/v1alpha1
name: codex                      # must equal the directory name, [a-z0-9-]+
version: 0.3.0                   # semver; bumped per release of this recipe
description: Codex agent in an egress-restricted container with a LiteLLM gateway
homepage: https://github.com/infrasecture/vaka-registry/tree/main/codex
tags: [agent, openai, litellm]
minVakaVersion: 0.1.0            # oldest vaka this recipe is tested with
env:                             # documents compose interpolation inputs
  - name: OPENAI_API_KEY
    required: true
    description: Forwarded to the LiteLLM gateway
  - name: WORKSPACE_DIR
    default: "./"
    description: Host directory mounted at /workspace
```

The `env` section is documentation-grade metadata (shown by `info` and after
`get`), not a template language: parameterization stays plain compose
interpolation + `.env`, which the codex recipe already uses.

## 4. The catalog: `index.yaml`

Generated by CI on every release; modeled on Helm's repository index:

```yaml
apiVersion: recipes.vaka/v1alpha1
generated: "2026-07-09T12:00:00Z"
recipes:
  codex:
    - version: 0.3.0
      description: Codex agent in an egress-restricted container ...
      tags: [agent, openai, litellm]
      created: "2026-07-09T11:58:03Z"
      digest: sha256:9f2a...
      urls:
        - https://github.com/infrasecture/vaka-registry/releases/download/codex-0.3.0/codex-0.3.0.tar.gz
      minVakaVersion: 0.1.0
      env: [...]                  # copied from recipe.yaml
      policy:                     # computed by CI from vaka.yaml + compose
        defaultActions: {codex: reject, litellm: reject}
        riskFlags: []             # see §7
    - version: 0.2.1
      ...
```

vaka caches each registry's `index.yaml` (with ETag/If-Modified-Since) under
the user cache dir; `vaka registry refresh` forces re-fetch. Search and `info`
work entirely from cached indexes — no network round-trip per query.

The `policy` block in the index is advisory (it makes search/info useful
before downloading); after fetching, vaka always **recomputes** the policy
summary and risk flags locally from the actual files and fails on mismatch
with the index — the index is a hint, never a trust anchor for content.

## 5. Multi-registry configuration

`$XDG_CONFIG_HOME/vaka/registries.yaml` (created on first use):

```yaml
apiVersion: recipes.vaka/v1alpha1
registries:
  - name: official
    url: https://infrasecture.github.io/vaka-registry/index.yaml
  - name: acme                    # added via `vaka registry add`
    url: https://recipes.acme.corp/index.yaml
```

Resolution rules:

- Qualified reference `acme/codex` → exactly that registry.
- Unqualified `codex` → resolved **only if the name is unique across all
  configured registries**; otherwise vaka errors and lists the qualified
  candidates. This is the anti-typosquatting rule: adding a registry can never
  silently hijack a name you already use (no ordering/priority games).
- `official` is built in; removing it is allowed but explicit.

## 6. CLI surface

All new names are safe under the compose-namespace restructure (`get`,
`search`, `recipes`, `registry` are not docker compose verbs).

```
vaka get <[registry/]name>[@version] [dir]    # fetch or update a recipe
vaka search [term]                            # search all registry catalogs
vaka recipes list                             # catalog listing (all registries)
vaka recipes info <[registry/]name>[@version] # metadata, env, policy, versions
vaka registry list                            # configured registries + cache age
vaka registry add <name> <index-url>
vaka registry remove <name>
vaka registry refresh [name]                  # re-fetch index(es)
```

`vaka get` semantics (the app-store verb, deliberately idempotent like
`docker pull`):

1. Resolve name and version (`@version` optional; default = highest semver).
2. Download tarball, verify `sha256` digest from the index, extract via the
   hardened extractor (§7) into a temp dir, then atomically move into place.
3. Target dir defaults to `./<name>`.
   - Dir absent → install.
   - Dir contains a matching `.vaka-recipe.lock` → **update**: compare
     current files against the lock's per-file hashes; if any tracked file was
     locally modified, refuse with a list and require `--force` (overwrite) —
     `.env` and files matching lock `userFiles` patterns are never touched.
   - Dir exists without a lock → refuse (never clobber unknown content).
4. Never runs docker/compose. Prints: version installed, digest, required env
   vars not yet set, locally computed policy summary + risk flags, and next
   steps (`cd codex && vaka up`).

Provenance lock written by `get` into the recipe dir:

```yaml
# .vaka-recipe.lock
apiVersion: recipes.vaka/v1alpha1
registry: official
name: codex
version: 0.3.0
digest: sha256:9f2a...
fetched: "2026-07-09T12:03:11Z"
files:                       # tracked files with content hashes
  compose.yaml: sha256:...
  vaka.yaml: sha256:...
  myCodex: sha256:...
userFiles: [".env"]          # user-owned; never installed, never overwritten
```

The lock makes every instantiated recipe self-describing (no global installed
database — `vaka recipes list` shows the catalog; a dir's provenance lives in
the dir, which also survives the user moving/copying it or committing it to
their own git repo).

## 7. Security design

Recipes are arbitrary code execution *by design* — a compose file can mount
`/`, bind the docker socket, or run privileged. The registry is therefore a
supply chain and must be treated like one:

**Transport & integrity.**
- HTTPS only for index and tarballs (`file://` allowed for local testing).
- Tarball digest verified against the index before extraction; mismatch is a
  hard fail and leaves any previous install untouched.
- The index itself is trusted via TLS to the registry origin in v1. The
  registries config reserves a `publicKey` field per registry: v2 adds a
  detached signature (`index.yaml.sig`, minisign/cosign) with the key pinned
  at `vaka registry add` time (TOFU), closing the compromised-CDN gap.

**Hardened tarball extraction** (dedicated, tested extractor):
- Reject path traversal (`..`, absolute paths) — zip-slip.
- Symlinks: allow only relative links resolving inside the recipe dir (the
  codex recipe legitimately ships `docker-compose.yaml → compose.yaml`);
  reject absolute or escaping targets.
- Reject hardlinks and device/special files; preserve the exec bit (launcher
  scripts like `myCodex`) but nothing else.
- Enforce limits: max unpacked size, max file count, max single-file size
  (decompression-bomb defense).
- Extract to temp dir + atomic rename; no partially-installed recipes.

**Risk surfacing (lint), not gatekeeping.** After every `get` (and computed by
CI into the index for search/info), vaka derives `riskFlags` from the actual
compose + vaka.yaml:
- `privileged`, `cap-add-broad` (SYS_ADMIN, ALL), `docker-socket-mount`,
  `host-network`, `host-pid/ipc`, `broad-bind-mount` (`/`, `$HOME`, ...),
  `egress-default-accept`, `no-policy-for-service` (service in compose without
  a vaka.yaml entry), `disables-vaka-init`.
- Flags are printed prominently; the official repo's CI *fails* on flags
  unless the manifest declares them with a justification
  (`riskAcknowledgements`). Third-party registries can be laxer — but vaka
  prints the same flags locally regardless of what the index claims.

**No execution.** `vaka get`/`search`/`info` never invoke docker, never run
recipe scripts, never read `.env`. The trust decision stays with the user at
`vaka up`, with the policy summary already on their terminal.

**Name integrity.** Unqualified names must be globally unique across
configured registries (§5). Recipe names are `[a-z0-9-]+` and must equal
their directory name; CI enforces it.

**Secrets hygiene.** CI refuses committed `.env` files and runs a secret scan;
the convention is `.env.example` + `env:` manifest metadata.

## 8. Registry repository CI (the authoring repo)

Reusable workflows shipped in the official repo (so third-party registries
get the same guarantees by copying two workflow files):

1. **validate** (every PR): for each changed recipe — `recipe.yaml` schema
   check, name/dir match, semver bump enforced when content changes,
   `docker compose config` parses, `vaka validate --compose` passes, README
   present, risk lint (fail on undeclared flags), secret scan.
2. **publish** (tag `<name>-<version>`): package `<name>-<version>.tar.gz`,
   compute digest, attach to a GitHub Release, regenerate `index.yaml`, and
   publish it (GitHub Pages branch or release asset behind a stable URL).

`examples/codex` migrates to the registry repo as the first recipe (the
in-repo example can remain as a pointer or a slim copy).

### Official hosting and scalability

The official registry lives on GitHub: authoring repo
`infrasecture/vaka-registry`, `index.yaml` served from GitHub Pages
(`https://infrasecture.github.io/vaka-registry/index.yaml`), tarballs attached
to GitHub Releases.

**Rule: vaka never calls the GitHub API.** The index embeds direct
`releases/download/...` asset URLs; asset downloads and Pages are CDN-backed
and are not subject to the unauthenticated API rate limit (60 req/h), which
listing releases via the API would be. This is the same serving model the Helm
chart-releaser ecosystem runs at large scale.

Scalability assessment of this backend:

- **Release assets**: 2 GiB/asset (recipes are KBs), no cap on release count,
  free CDN bandwidth for public repos. Not a bottleneck at any realistic
  recipe count.
- **The monolithic index is the first thing to outgrow** (Helm's `stable`
  index reached ~16 MB before sharding). Mitigations, in order: the index
  carries only the most recent N versions per recipe (default 5; older
  versions stay downloadable via their release URLs), YAML compresses ~10× on
  the wire, and ETag caching means an unchanged index costs one 304. If the
  catalog ever grows past that, shard to per-recipe metadata files — or move
  the backend to OCI artifacts (see below).
- **Tag accumulation**: one `<name>-<version>` tag per release accumulates in
  the authoring repo. Cosmetic; the alternative (committing tarballs to a
  gh-pages branch) permanently bloats clones, so Releases wins.
- **OCI escape hatch**: because a registry is abstracted as "catalog + artifact
  URL + digest", a future backend can publish recipes as OCI artifacts on
  `ghcr.io` (tags, content-addressed digests, dedup — the literal
  docker-registry model) by teaching the fetcher an `oci://` URL scheme. No
  CLI, index-schema, or lock-format changes required. Not planned; kept open.

## 9. Implementation sketch (in this repo)

New packages, keeping `cmd/vaka` thin like the compose path:

- `pkg/registry`: registries config load/save, index fetch+cache (ETag),
  index model, name resolution (uniqueness rule), semver selection.
- `pkg/recipe`: manifest + lock models, hardened tar extractor, digest
  verification, install/update engine (hash comparison), risk lint (reuses
  `compose-go` and `pkg/policy` already in go.mod; policy summary reuses
  `loadAndValidate`).
- `cmd/vaka`: `get.go`, `search.go`, `recipes.go`, `registry.go` — normal
  cobra commands under a new `Recipe Commands:` group (root help gains a third
  group). No pre-parser changes needed; these are plain native commands.
- Test seams mirror the compose path: an `httpFetcher` hook (like
  `execDockerComposeFn`) so all commands are testable offline with fixture
  indexes/tarballs; extractor gets adversarial-archive tests (traversal,
  symlink escape, bombs).

Dependencies: stdlib `net/http`, `archive/tar`, `compress/gzip`; semver needs
`golang.org/x/mod/semver` (tiny) or a hand-rolled comparator. No git binary,
no go-git, no YAML lib beyond the existing `gopkg.in/yaml.v3`.

### Phasing

1. **Phase 1 — read-only consumption**: registries config + `official`
   default, index fetch/cache, `vaka search`, `vaka recipes list|info`,
   `vaka get` (install + idempotent update, digest verify, hardened extract,
   lock file, local risk lint). Registry repo with codex recipe + CI.
2. **Phase 2 — management & polish**: `vaka registry add|remove|refresh`
   UX hardening, `vaka recipes info` full version history, shell completion
   for recipe names (from cached index), `minVakaVersion` enforcement.
3. **Phase 3 — provenance hardening**: signed indexes (key pinned at
   `registry add`), `vaka get name@sha256:...` digest pinning, `vaka recipes
   verify` (re-check a dir against its lock).

## 10. Future perspective: composable recipes

Out of scope for this design, but it informs several choices above: recipes
should eventually be able to *share* infrastructure — the canonical case is a
single LLM-proxy sidecar (LiteLLM) serving several agent recipes instead of
each stack running its own copy.

The future mechanism is compose-native, not an orchestrator: shared
infrastructure is itself a recipe (e.g. `litellm-proxy`) that exposes a
well-known external docker network; consumer recipes join it
(`networks: ... external: true`) and reach it by service alias. vaka.yaml
needs nothing new — its egress `to:` entries are already name-based, and
names resolve the same way across a shared network. A later `vaka up` can
resolve declared dependencies and ensure providers are running (compose
already tolerates externally-managed projects on shared networks).

What this reserves or pins **today**:

1. **Reserved manifest fields**: `provides:` and `requires:` are reserved in
   `recipe.yaml` — the schema validator rejects them until a future
   `apiVersion` specifies their semantics, so third-party registries cannot
   squat them with incompatible meanings. The envisioned shape:
   `requires: [{recipe: litellm-proxy, version: ">=0.2"}]` /
   `provides: [{service: litellm, network: vaka-llm}]`.
2. **Fine-grained packaging**: one recipe = one tarball (never multi-stack
   bundles), so a sidecar can be factored out into its own recipe without a
   packaging change.
3. **Flat unique names + per-recipe semver**: exactly what dependency
   references will point at; nothing to rename later.
4. **Lock extensibility**: `.vaka-recipe.lock` records
   registry/name/version/digest per directory; a dependency graph extends the
   same file rather than requiring new state.
5. **Authoring guideline**: recipes should give externally-consumable services
   stable network aliases, since cross-recipe policy (`to: [litellm]`) and
   discovery will hang off those names.

Explicitly *not* on the table, ever: scheduling, placement, lifecycle
ownership of shared services beyond "ensure it is up" — that is where
reinventing kubernetes begins.

## 11. Open questions

1. Should `vaka get` with no lock but an *empty* existing dir proceed?
   (Proposed: yes — empty dir is safe.)
2. Per-recipe versioning granularity: strict semver per recipe (proposed) vs
   registry-wide releases. Strict semver matches the app-store UX and makes
   `minVakaVersion` + updates coherent.
3. Does `vaka recipes list` also scan the current directory tree for
   instantiated recipes (lock files) to show "installed here"? (Proposed:
   Phase 2, `vaka recipes list --here`.)
